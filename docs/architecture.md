# greenbuild — архитектура и план MVP

Sep 30, 2026 · @Arslan · обновлено 11 октября 2026

## Обзор и позиционирование

greenbuild — ежедневная игра для DevOps и облачных инженеров, в которой проверенный навык становится публичным сертификатом. Бизнес-модель — маркетплейс найма: компании платят за доступ к кандидатам с доказанным уровнем, для игроков всё бесплатно и без рекламы. Главный риск на этапах 0–2 — удержание: без игроков, которые возвращаются, маркетплейса не будет, поэтому основная часть документа строит игру и сигнал.

**Для кандидата:** бесплатный публичный профиль-сертификат навыков, который растёт с каждым решённым заданием и открывает предложения работы — только с его согласия.

**Для компании:** поиск инженеров по реальному рейтингу навыков вместо ключевых слов, приватные задания для своих кандидатов, меньше времени на технические собеседования.

**Почему сейчас:** найм джуниоров сократился, мидлов ищут по конкретным навыкам (облака, Kubernetes, CI/CD), а ИИ обесценил резюме и домашние задания. Работодателям нужен проверяемый сигнал.

**Первый сегмент спроса:** удалённые стартапы и продуктовые компании (20–500 человек) в США и ЕС, которые нанимают DevOps/Cloud/SRE уровня mid–senior, в том числе из СНГ и Центральной Азии.

**Первый сегмент предложения:** DevOps и облачные инженеры с 2–8 годами опыта, русско- и англоязычные.

### Архитектурные принципы

1. **Модульный монолит** для API: один сервис, чёткие модули внутри. Микросервисы — только когда модуль реально упрётся в нагрузку.
2. **Движок песочниц разделён надвое:** control plane в сети приложения, ноды песочниц — в изолированной сети без доступа к данным.
3. **Stateless API.** Всё состояние — в PostgreSQL и Redis, копии API взаимозаменяемы.
4. **Нейтральная к языку очередь** (Redis Streams, затем Azure Service Bus) между API на TypeScript и движком на Go.
5. **Инфраструктура как код с первого дня** (Terraform).
6. **Песочница — недоверенная зона.** Всё, что там выполняется, считается враждебным.
7. **Приватность по умолчанию.** Кандидат невидим для компаний, пока сам не включит поиск; до взаимного согласия компания видит только анонимную карточку.
8. **Профиль — это сертификат с первого дня.** Публичный профиль проектируется одновременно с тем, как его увидит компания.

### Границы MVP (этапы 0–2)

- Нет мобильного приложения (только адаптивный PWA). Пока экраны фиксированы на 1280 px — см. «Интерфейс и Figma» и решение D5.
- Нет открытой регистрации компаний и платного поиска: на этапах 1.5–2 работают только приглашённые дизайн-партнёры (оценки своих кандидатов и бесплатный ранний поиск).
- Нет пользовательских заданий от сообщества.
- Нет Kubernetes-заданий внутри песочницы.
- Нет видео-прокторинга.

Основная часть документа — этапы 0–2. Всё, что нужно только с этапа 3 (кабинет компании, цены, полная схема спроса, юридические детали, метрики спроса, GTM), вынесено в приложение «Позже» в конце; числа там — гипотезы.

## Схема системы

Браузер ходит через единый вход: страницы и REST — в сеть приложения, терминал по WebSocket — к control plane движка, который проксирует его на ноду. API только кладёт задачу в очередь Redis Streams. Ноды песочниц живут в изолированной сети и принимают команды только от control plane по mTLS; маршрута к базе, Redis и API у них нет. Внешние сервисы (GitHub OAuth, Claude API, Stripe, Container Registry, ATS) вызываются из API, worker и CI и на схеме не показаны.

## Валидность сигнала

Компании платят только за сигнал, который предсказывает результат собеседования и работы; до этапа 3 это нужно доказать на данных дизайн-партнёров, а методику опубликовать.

### Как измеряем

1. **Согласованность с собеседованием.** Дизайн-партнёры оценивают кандидатов с рейтингом по своей шкале (1–5), не видя рейтинга; считаем корреляцию. Порог успеха задаётся после первых 20–30 кандидатов — до этого его неоткуда взять.
2. **Устойчивость.** Повторная оценка того же навыка через 30 дней близка к первой.
3. **Отзыв после контакта (этап 3).** Компания отмечает, подошёл ли кандидат по уровню.
4. **Честность.** Доля аннулированных после ревью попыток в выдаче остаётся низкой и не растёт.

### Что показываем компании

- Рейтинг по навыку с доверительным интервалом (из Glicko-2), а не голое число.
- Число решённых заданий по навыку и дату последней активности.
- Отметку Verified и дату проверки.
- Процентиль среди активных игроков навыка.

### Справедливость

Система ранжирует кандидатов для работодателей, поэтому раз в год проводится аудит на смещение (disparate impact) по доступным признакам, результаты публикуются. Рейтинг не использует страну, пол, возраст, имя; страна — только фильтр, который включает сама компания для юридических ограничений найма.

### Временная авторизация (dev-токен)

До Auth.js API принимает dev-токен пользователя: JWT HS256, подписанный `DEV_AUTH_SECRET`, аудитория `greenbuild-dev-user`, id пользователя — UUID. `SessionGuard` (бывший `DevUserGuard`) и декоратор `@CurrentUser()` в API его проверяют; в production guard не пускает никого. Веб при первом заходе на `/play` выдаёт случайному id httpOnly-cookie `gb_dev_session` (SameSite=Lax), а серверные обработчики `/api/*` пересылают запросы в API с этим токеном. Изменяющие запросы требуют заголовок `x-greenbuild-request: 1` (защита от CSRF).

Как убирается: Auth.js в `apps/web` выдаёт сессию, API проверяет короткоживущий подписанный токен за тем же интерфейсом `@CurrentUser()` (задачи 30a–30c). Playwright переходит на тестовый провайдер входа (30d), и только после этого отдельной задачей удаляются проверка dev-токена в `SessionGuard`, скрипт `dev:user-token`, выдача `gb_dev_session` и `DEV_AUTH_SECRET` (30e). Решение по CSRF пересматривается там же.

## Структура монорепо

Один репозиторий на pnpm workspaces + Turborepo; общие типы и схемы живут в `packages`, приложения — в `apps`. Ниже — фактическая структура; новые пакеты создаются задачей, которой они впервые нужны (исключение — пустая заготовка `packages/ui`, оставшаяся с начала проекта).

```
greenbuild/
├─ apps/
│  ├─ web/             # Next.js 16: экраны игрока; e2e/ — Playwright
│  ├─ api/             # NestJS 12: модульный монолит (модули attempts — старт, проверки, подсказки, сдаться, возобновление; challenges — карточка и каталог; users — `GET`/`PATCH /v1/me`; health; служебные auth — dev-токен и `@Public()`, engine — клиент движка, infra, config, errors)
│  ├─ sandbox-engine/  # Go: control plane, /attach, /internal, consumer очереди, лог сессий
│  ├─ sandbox-agent/   # Go: агент ноды, gRPC с mTLS, TTL-reaper; cmd/sandbox-shell
│  ├─ worker/          # TypeScript: /health и публикация outbox в Redis Streams (задача 20b)
│  └─ mobile/          # этап 4: Expo (ещё не создан)
├─ packages/
│  ├─ shared/          # zod-схемы (API, очередь, манифест задания), ошибки, константы
│  ├─ db/              # Drizzle-схема, миграции, сид, отчёт для ворот (`pnpm report:gate`)
│  ├─ queue/           # JSON Schema сообщений очереди (источник истины) + типы Go
│  ├─ agent-api/       # agent.proto и сгенерированный Go-код
│  ├─ devpki/          # одноразовый CA и сертификаты для локального mTLS
│  ├─ challenge-spec/  # валидатор и CLI заданий (`pnpm challenges:validate`)
│  ├─ redactlog/       # Go: маскирование секретов в логах (slog)
│  ├─ ui/              # пустая заготовка; общие компоненты — когда понадобятся
│  ├─ testkit/         # тестовые помощники: одноразовые контейнеры Docker для тестов API и worker
│  └─ config/          # eslint, tsconfig, prettier с лимитами размера
├─ challenges/         # исходники заданий; verify-challenge.sh
├─ scripts/            # play.mjs и play-stack.sh (pnpm play:up / play:down); run-go-app.mjs (Go-бинарники в pnpm dev); check-dev-stop.ps1
├─ infra/
│  ├─ docker/          # play-stack.compose.yaml (PostgreSQL и Redis для локального стека)
│  └─ terraform/       # пустая заготовка; задача 28
├─ docs/
│  ├─ architecture.md  # этот документ (на русском)
│  ├─ progress.md      # статус задач (на английском)
│  ├─ adr/             # ADR-001…012 — PR задачи 38, ждёт одобрения владельца
│  ├─ legal/           # пусто; тексты — после консультации юриста
│  ├─ security/        # sandbox-escape-checklist.md (задачи 34a–34b)
│  └─ runbooks/        # play-locally.md, challenge-authoring.md, sandbox-node.md
└─ .github/workflows/
```

Целевые модули API (из первоначального плана; создаются задачами, которым они нужны): `auth/` (вход, сессии, возраст), `users/` (профиль, режим видимости), `challenges/` (каталог, задание дня, версии), `attempts/` (старт, проверка, результат), `game/` (XP, рейтинг, стрики, уровни), `leaderboards/`, `anticheat/` (сигналы, флаги, ревью), `consent/` (режимы, запросы, принятие, отзыв), `privacy/` (экспорт, удаление, сроки хранения), `companies/` (аккаунты, команда, верификация), `search/`, `assessments/` (приватные задания), `trust/` (жалобы, санкционный скрининг, репутация), `billing/` (Stripe, кредиты, лимиты), `integrations/` (ATS, вебхуки), `notifications/`.

`CLAUDE.md` с правилами разработки хранится локально и исключён из git (решение владельца); лимиты размера при этом проверяют ESLint, golangci-lint, CI и Husky. Документация пишется на английском, кроме этого файла.

Правила зависимостей: `apps` зависят от `packages`, но никогда друг от друга. API и движок общаются только через очередь и внутренний HTTP-контракт. API никогда не управляет контейнерами — только ставит задания в очередь. Доступ к БД — только через `packages/db`. Общие типы и zod-схемы — только в `packages/shared`.

## Модель данных

Все ID — UUID v7; все таблицы имеют `created_at` и `updated_at`; мультитенантность через `company_id` и таблицы согласия создаются на этапе 0, даже если кабинет открывается позже.

## Спецификация задания

Задание — это папка в `challenges/` с манифестом, Docker-образом, скриптом поломки и скриптом проверки; CI собирает её в неизменяемую версию.

```
challenges/nginx-502-upstream/
├─ challenge.yaml     # манифест
├─ Dockerfile         # базовое состояние среды
├─ setup.sh           # ломает среду по seed
├─ check.sh           # exit 0 = решено
├─ solution.sh        # эталонное решение (для CI)
├─ hints.md           # 1–3 подсказки по уровням
└─ README.md          # разбор после решения
```

```yaml
id: nginx-502-upstream         # совпадает с именем папки
version: 1                     # опубликованная версия не меняется; исправление = новая версия
title: "Сайт отдаёт 502"
statement: "Пользователи видят 502. Верни сайт в строй."
difficulty: 4                  # 1–10
skills: { linux: 0.4, nginx: 0.6 }   # веса навыков, сумма = 1
time_limit_sec: 900            # 60–7200
resources: { cpu: "500m", memory: "512Mi", disk: "1Gi" }
network: none                  # пока принимается только none; allowlist не построен
capabilities: [CHOWN, SETUID, SETGID]   # возврат только из allowlist агента
randomize:                     # подставляется в setup.sh по seed
  app_port: { range: [3000, 3999] }
  app_user: { pick: [svc, webapp, runner] }
check:
  command: /opt/greenbuild/check.sh
  timeout_sec: 20
  run_as: root                 # checker не виден пользователю
hints: 3                       # число подсказок в hints.md
source: human                  # human / ai / community / company
```

Пример показывает форму, а не точные значения: истина — zod-схема `challengeManifestSchema` в `packages/shared`.

Отличия от первоначального плана:
- `skills` — словарь весов, сумма которых равна 1.
- Добавлен ключ `capabilities`. Он возвращает только capabilities из allowlist агента (CHOWN, DAC_OVERRIDE, FOWNER, KILL, NET_BIND_SERVICE, SETGID, SETUID).
- Ключ рандомизации называется `app_port`, а не `upstream_port`.
- Путь проверки — `/opt/greenbuild/check.sh`.
- `network` принимает только `none`.
- В `source` есть значение `company`.
- `time_limit_sec` — от 60 до 7200.

### Где живёт схема

- **zod-схема манифеста** — `packages/shared` (правило: общие zod-схемы только там).
- **Валидатор папки и CLI** (`pnpm challenges:validate`) — `packages/challenge-spec`. Он проверяет обязательные файлы, манифест, совпадение id с папкой и число подсказок. Запускается в CI в задаче «Lint, typecheck, test, build» (задача 23a).
- **JSON Schema для редакторов** — `packages/challenge-spec/challenge.schema.json`, генерируется из zod-схемы командой `pnpm challenges:schema`; тест падает, если файл не перегенерирован. Первая строка `challenge.yaml` подключает её: `# yaml-language-server: $schema=../../packages/challenge-spec/challenge.schema.json`. Правила между полями (сумма весов навыков, порядок в `range`) проверяет только `challenges:validate`.

`verify-challenge.sh` берёт манифест в JSON из `packages/challenge-spec` (`dist/inspect.js`, задача 23c), который сначала проверяет папку. Сид (`db:seed`) обходит `challenges/*` через тот же валидатор и добавляет новые задания и версии; если у уже записанной версии изменились манифест или `check.sh`, сид останавливается и просит новую версию (задача 23d).

### Жизненный цикл версии

1. Автор или ИИ создаёт папку по потоку из задачи 24 и открывает PR.
2. CI валидирует папку и манифест (`challenges:validate`).
3. CI собирает образ, запускает `setup.sh` с тремя разными seed под gVisor и проверяет, что `check.sh` возвращает **не** 0 (среда реально сломана).
4. CI запускает `solution.sh` и проверяет, что `check.sh` возвращает 0 (задание решаемо).
5. Автоматические проверки чек-листа (задача 24); ручного ревью нет (решение D3).
6. После слияния образ пушится в Azure Container Registry, сид записывает версию с digest образа (задача 28g).
7. Модератор переводит статус в `live`.

Шаги 2–4 выполняет CI: `challenges:validate` в основной задаче и `verify-challenge.sh` под gVisor в задаче «Challenges (gVisor)» — для папок, изменённых в PR (для всех — на main или если изменились сам скрипт или валидатор). Та же задача проверяет, что намеренно несломанная фикстура `packages/challenge-spec/fixtures/unbroken` отклоняется. Шаг 6 работает только локально (`pnpm play:up`).

### Поток создания заданий

Черновик пишет ИИ по короткому брифу, следуя чек-листу; человек не ревьюирует (решение D3: автоматически); CI проверяет папку, решаемость под gVisor и то, что можно проверить из чек-листа. Поток собирается задачей 24.

Чек-лист автора (`docs/runbooks/challenge-authoring.md`); пункты 2 и 7 и часть пунктов 3–5 проверяет CI:
1. Одна проблема на задание; причина находится в логах или конфигах среды, а не в условии.
2. Seed реально меняет то, что нужно найти (порты, имена, пути).
3. Опытный инженер решает за 3–10 минут.
4. `check.sh` проверяет результат, а не способ решения, и не принимает «обходы» (например, удаление сервиса).
5. Подсказки идут от общего к конкретному, ни одна не содержит готовой команды.
6. Разбор (`README.md`) объясняет причину и как её найти.
7. В образе нет решения, `check.sh` и `solution.sh`.

### Правила

- Версии неизменяемы: исправление = новая версия, старые попытки ссылаются на свою.
- `check.sh` и `solution.sh` не попадают в образ пользователя: checker копируется в песочницу только в момент проверки.
- Одно задание — одна проблема. Длинные цепочки поломок только на сложности 8+.
- Время на решение опытным инженером — 3–10 минут; всё дольше идёт в формат «лабораторной», а не ежедневного задания.

### Утечки и ротация

- Разбор решения доступен только тем, кто решил задание или сдался, и не индексируется поисковиками; копирование текста разбора отключено.
- Worker каждую неделю сравнивает долю решений и медианное время каждой версии с `solve_rate_baseline`. Рост доли решений на 30% или падение медианы вдвое → версия помечается как возможно утёкшая.
- Утёкшая версия выводится из рейтинговых режимов (retired, причина `leak_suspected`) и заменяется новой версией с другими параметрами поломки.
- Задания для приватных оценок компаний не публикуются в общем каталоге и не имеют публичного разбора.
- Задание дня не повторяется раньше чем через 180 дней.

## Движок песочниц

Движок состоит из двух программ на Go: control plane в сети приложения (очередь, TTL, проверки, WebSocket-прокси) и агент на каждой ноде песочниц, который принимает команды только от control plane по mTLS и не имеет доступа ни к чему другому.

### Разделение ответственности

| Компонент | Где живёт | Доступ | Что делает |
| --- | --- | --- | --- |
| Control plane | VNet core (Container Apps) | Redis, Blob Storage, внутренний API; исходящий mTLS к агентам | Читает очередь, выбирает ноду, держит пул, проксирует терминал, запускает проверки, пишет логи |
| Агент ноды | VNet sandbox, каждая нода | Только входящий mTLS от control plane; исходящего трафика нет, кроме ответа | Запускает и уничтожает контейнеры, отдаёт PTY-поток, копирует checker |
| Контейнер попытки | Нода, рантайм gVisor/Kata | Никакого | Среда пользователя |

### Жизненный цикл одной попытки

1. Пользователь жмёт «Начать». API создаёт `attempt` со случайным `seed` и пишет сообщение `sandbox.create` в Redis Stream.
2. Control plane читает сообщение (consumer group), выбирает ноду со свободным слотом и командует агенту запустить контейнер из образа по digest с лимитами из манифеста.
3. Агент выполняет `setup.sh` с seed и удаляет скрипт. Control plane пишет `sandbox.status = ready`.
4. API выдаёт клиенту короткоживущий токен (JWT, 60 секунд на подключение), привязанный к attempt и пользователю.
5. Браузер открывает WebSocket к control plane; тот проверяет токен и открывает PTY через агента. xterm.js ↔ control plane ↔ агент ↔ контейнер.
6. Control plane пишет каждый ввод с отметкой времени в буфер сессии.
7. «Проверить» → control plane через агента копирует checker, запускает, удаляет, возвращает результат. Лимит — 10 проверок.
8. Решено, время вышло, 5 минут без активности или пользователь сдался → контейнер уничтожается, лог уходит в Blob Storage, в `sandbox.status` публикуется `destroyed` с причиной. API переводит попытку в конечный статус и публикует `attempt.finished` через outbox. Всё это построено (задачи 17–20) — см. «Что построено и чего нет».

### Пул прогретых песочниц

Для задания дня агенты держат заранее поднятые контейнеры (без setup), чтобы старт занимал 1–2 секунды вместо 10–20. Размер пула задаётся по трафику предыдущего дня.

### Изоляция и лимиты

| Мера | Как |
| --- | --- |
| Рантайм | gVisor (runsc) на старте; Kata Containers через AKS Pod Sandboxing при росте нагрузки |
| Пользователь | Внутри root, снаружи — непривилегированный UID (user namespaces) |
| Сеть контейнера | По умолчанию `none`; для заданий с сетью — отдельный namespace без выхода в интернет |
| Сеть ноды | VNet sandbox без пиринга к данным; входящий трафик только от control plane, NSG запрещает всё остальное |
| Ресурсы | CPU, память, диск, PID-лимит (256; под gVisor 512, отклонение 31), лимит открытых файлов |
| Время | Жёсткий TTL из манифеста + 2 минуты, затем принудительное уничтожение агентом, даже без связи с control plane |
| Файловая система | Корень только для чтения, где задание позволяет; writable-слой ограничен |
| Capabilities | Сброшены все, кроме явно указанных в манифесте |
| Системные вызовы | Профиль seccomp поверх gVisor |
| Злоупотребления | CPU 100% дольше 60 секунд → контейнер убит, попытка помечена |

### Контракты

- Схемы сообщений очереди лежат в `packages/queue` как JSON Schema — это источник истины. Go-типы и zod-копии в `packages/shared` написаны вручную; тест на расхождение сверяет их со схемами.
- Stream `sandbox.create` → `{version, attempt_id, image, seed, cpu_millis, memory_bytes, ttl_seconds, network, capabilities}`; сейчас `image` — ссылка на образ, digest — задача 28g
- Stream `sandbox.status` (control plane → API): `ready`, `failed`, `destroyed` + причина (`destroyed` публикуется с задачи 17a)
- Stream `attempt.finished` (публикует API через outbox и worker, задача 20) → `{attempt_id, user_id, challenge_version_id, status, duration_ms, checks_used, finished_at}`
- Stream `sandbox.destroy` (API → control plane, задача 19a) → `{attempt_id, sandbox_id, reason}`
- HTTP (внутренний) `POST /internal/attempts/{id}/check` → `{passed, output_tail, duration_ms}`
- gRPC control plane → агент по mTLS: `CreateSandbox`, `Exec`, `CopyIn`, `Run`, `Destroy`, `Health`
- WebSocket `wss://sbx.greenbuild.dev/attach?token=…`

## Игровая механика

Два независимых счётчика: XP вознаграждает регулярность и растёт всегда, а рейтинг навыка (Glicko-2) показывает реальный уровень и может падать — компании смотрят только на рейтинг.

### XP и уровни

- Решение: базовые XP = 10 × сложность.
- Бонус за скорость: до +50% по сравнению с медианным временем решения этого задания.
- Подсказки: −20% за каждую использованную.
- Задание дня: ×1.5. Первое решение нового навыка: +25 XP.
- Уровень n требует суммарно 100 × n^1.5 XP (кривая пологая в начале, круче потом).
- Все начисления — через `xp_ledger`, сумма считается и кэшируется.

### Рейтинг навыка (Glicko-2)

Попытка — это «матч» пользователя против задания: у задания тоже есть рейтинг, который хранится в challenge\_versions (rating, rating\_deviation) и калибруется по результатам всех игроков. Решил быстро сложное задание → рейтинг растёт сильно; не решил лёгкое → падает. Glicko-2 учитывает неопределённость (`rating_deviation`): новичок быстро выходит на свой уровень, а опытный не скачет от одной неудачи.

- Рейтинг считается по каждому навыку с весами из `challenge_skills`.
- Общий рейтинг = взвешенное среднее по навыкам с достаточной уверенностью.
- Пересчёт — фоновой задачей `worker` после `attempt.finished`.
- Попытки с флагом античита в рейтинг не идут, пока не прошли ревью.

### Стрики

- «День» — календарный день в timezone пользователя, которую он выбирает в профиле; менять можно раз в 30 дней, чтобы нельзя было «выиграть» день сменой пояса.
- Стрик +1 за любое решённое задание за день (не обязательно задание дня).
- Заморозка: 1 бесплатная за каждые 7 дней стрика, максимум 3 в запасе. Автоматически тратится на пропущенный день.
- Напоминания: email вечером по местному времени, если сегодня ещё не решено (этап 4 — push).

## Античит

Защита строится на трёх слоях: задания, которые трудно списать, поведенческие сигналы из песочницы и ручная проверка перед показом компаниям; камеры в ежедневной игре нет.

### Слой 1 — задания, устойчивые к списыванию

- Уникальные параметры по seed: порты, имена пользователей, пути, значения в логах разные у каждого.
- Суть проблемы в среде, а не в условии: условие — одна фраза, ответ нужно найти в логах и конфигах.
- Короткий лимит времени.

### Слой 2 — сигналы

| Сигнал | Как считается | Вес |
| --- | --- | --- |
| paste\_large | Вставка больше 200 символов одним блоком | Средний |
| idle\_then\_solve | Нет ввода больше 70% времени, затем решение с первой попытки | Высокий |
| no\_exploration | Решение без единой команды чтения (cat, ls, journalctl, logs…) | Высокий |
| instant\_solve | Время меньше 20% медианы для задания | Средний |
| rating\_jump | Результат на 400+ пунктов выше текущего рейтинга | Средний |
| tab\_hidden | Вкладка скрыта больше 50% времени (Page Visibility API) | Низкий |
| same\_solution | Одинаковая последовательность команд у разных аккаунтов | Высокий |
| multi\_account | Совпадение устройства или IP с другим активным аккаунтом | Средний |

Сумма весов выше порога → `attempts.flagged = true`: XP начисляется, стрик засчитывается, но рейтинг не меняется до ревью. Так честный игрок с ложным срабатыванием не теряет серию.

### Слой 3 — Verified (этап 3)

Перед показом профиля компаниям пользователь по желанию проходит короткую живую сессию: решает задание и объясняет ход мыслей (созвон 15 минут или запись экрана с камерой с явным согласием). Результат — значок Verified. Биометрия лица не анализируется и не хранится; согласие на запись фиксируется отдельно, запись удаляется через 30 дней (требования BIPA в Иллинойсе и аналогичных законов штатов).

### Наказания

- Первое подтверждённое нарушение: попытка аннулирована, предупреждение.
- Повторное: сброс рейтинга по навыку.
- Систематическое: бан аккаунта и связанных аккаунтов.

### Правила

- **Каждый эндпоинт явно объявляет доступ.** По умолчанию нужна сессия; публичный эндпоинт помечается `@Public()`. Тест обходит все маршруты API и сверяет список публичных с этим документом (задача 30c). Сейчас публичны `/health` и `/v1/users/{handle}` (задача 46a). Запланирован как публичный `GET /v1/share/{token}.png` (этап 2). `GET /v1/challenges/{slug}` сейчас требует сессию.
- Одна активная попытка на пользователя (частичный уникальный индекс `attempts_one_active_per_user`).
- Статусы попытки меняет только сервер и только вперёд: повтор события ничего не меняет. Клиент опрашивает до `ready` (Server-Sent Events с этапа 4).
- Ошибки в едином формате: `{code, message, details}`; соответствие HTTP-статусам живёт в API.
- Защита от CSRF — обязательный заголовок `x-greenbuild-request: 1` на изменяющих запросах `/api/*` плюс cookie SameSite=Lax. Решение пересматривается вместе с Auth.js (задача 30e).
- Поиск никогда не возвращает личные поля кандидата до принятия запроса — проверяется контрактными тестами.
- Административные эндпоинты — под `/v1/admin`, только role=admin, все действия в `audit_log`.

### Права пользователя

- **Доступ и переносимость:** `POST /v1/me/export` — архив JSON со всеми данными, включая историю согласий и список компаний, получивших доступ.

- **Удаление:** `DELETE /v1/me` — мгновенное скрытие, отзыв всех согласий, удаление персональных данных в течение 30 дней; попытки обезличиваются и остаются только для калибровки рейтинга заданий.

### Минимизация

- Не собираем дату рождения — только подтверждение 18+ при включении поиска.
- Не собираем точный адрес и город: страна и часовой пояс достаточны.
- Сырые логи сессий удаляются через 90 дней, остаются производные сигналы.
- IP-адреса хранятся 30 дней для защиты от мультиаккаунтов, затем удаляются.

### Сети

- VNet `core`: web, API, worker, control plane движка; PostgreSQL, Redis и Blob Storage — через Private Endpoints, без публичных IP.
- VNet `sandbox`: только ноды песочниц с агентом; без пиринга к данным; NSG разрешает входящий mTLS только от подсети control plane и запрещает весь исходящий трафик, кроме ответов.
- Публичный вход на старте — DNS + TLS на ingress Container Apps (веб, API, WebSocket control plane); Azure Front Door с WAF подключается при росте нагрузки.

## Наблюдаемость, безопасность, CI/CD

Главные метрики — время старта песочницы и доля успешных запусков: если песочница не поднялась, пользователь уходит.

### Метрики и алерты

| Метрика | Цель | Алерт |
| --- | --- | --- |
| Время от «Начать» до ready (p95) | < 5 с (с пулом), < 20 с (без) | p95 > 30 с в течение 5 минут |
| Доля неудачных запусков песочниц | < 1% | > 3% за 10 минут |
| Длина очереди sandbox.create | < 20 | > 100 |

Продуктовые метрики (PostHog): удержание D1, D7, D30; медианная длина стрика; доля начатых и решённых попыток; воронка «регистрация → первое решение».

Метрики стороны компаний до этапа 3 — только три: оплатила ли компания, отправляет ли она приглашения каждую неделю, продлила ли подписку. Полная воронка спроса имеет смысл с \~20 компаний и лежит в приложении.

### Безопасность приложения

- Секреты только в Key Vault, доступ через Managed Identity, никаких ключей в коде.
- Сессии: httpOnly, Secure, SameSite=Lax cookie; для изменяющих запросов — обязательный заголовок `x-greenbuild-request: 1` (пересмотр вместе с Auth.js, задача 30e).
- Rate limiting на входе, регистрации и старте попыток (Redis).
- Зависимости: Dependabot и `pnpm audit`, образы сканируются Trivy в CI.
- Бэкапы PostgreSQL: автоматические, хранение 14 дней, проверка восстановления раз в месяц.
- Данные пользователей: экспорт и удаление аккаунта по запросу (нужно для GDPR и законов штатов США).

### CI/CD (GitHub Actions)

1. **PR**: линт, типы, юнит-тесты, сборка всех приложений (Turborepo кэширует неизменённое).
2. **PR с изменением в `challenges/`**: валидация манифеста, сборка образа, прогон setup → check (fail) → solution → check (pass).
3. **Merge в main**: сборка образов, пуш в ACR, миграции БД, деплой в staging, e2e-тесты (Playwright: вход → старт задания → решение → результат).
4. **Ручное подтверждение**: деплой в prod через ревизии Container Apps (откат одним действием).
5. **Terraform**: `plan` в PR, `apply` только после merge и ручного подтверждения.

**Сейчас:** на PR выполняются lint, typecheck, unit-тесты, build, проверка размера PR, «Sandbox integration (gVisor)», «Challenges (gVisor)» и «Slice e2e (Playwright)»; `challenges:validate` и проверка сгенерированного gRPC-кода (37a) — в основной задаче. CI-задач для Terraform (28a) и деплоя в staging (28g) ещё нет. С 8 октября 2026 GitHub Actions не запускаются (оплата); до восстановления те же проверки выполняются локально перед слиянием, а PR пишет, что CI и gVisor не проверялись (решение владельца).

# Позже: этап 3 и дальше

Всё в этом приложении — проработка на будущее, а не план работ на ближайшие месяцы. Каждое число здесь — гипотеза, которая проверяется на дизайн-партнёрах и данных этапов 1.5–2; решения пересматриваются перед стартом этапа 3.

## Принципы маркетплейса

Ценность для компании — время до качественного контакта, а не количество профилей; поэтому каждое правило ниже защищает качество обеих сторон.

1. **Кандидат контролирует доступ.** Никакой контакт без его согласия; отказ не требует объяснений компании, но причина собирается для репутации компании.
2. **Качество спроса важнее объёма.** Компании получают ограниченные кредиты на контакт; низкий процент принятия автоматически снижает лимиты.
3. **Сигнал, а не самоописание.** Поиск идёт по рейтингу навыков из реальных заданий; самоописание кандидата вторично.
4. **Verified по умолчанию в выдаче.** Компания сначала видит кандидатов, прошедших проверку; остальные — по фильтру.
5. **Платформа зарабатывает на доступе, а не на факте найма.** Модель не зависит от отслеживания найма, поэтому уход общения с платформы не ломает экономику.

### Ликвидность

| Метрика | Цель к концу этапа 3 |
| --- | --- |
| Доля поисков с ≥ 10 подходящими кандидатами | ≥ 70% |
| Принятие запросов на контакт | ≥ 35% |
| Время от первого поиска компании до первого принятого контакта | ≤ 7 дней |
| Доля открытых к предложениям кандидатов с ≥ 1 запросом в месяц | ≥ 25% |
| Доля компаний с ≥ 1 принятым контактом за 30 дней | ≥ 60% |

### Дезинтермедиация

После принятия контакта общение неизбежно уходит в почту и мессенджеры. Модель это принимает: компания платит за подписку с местами и кредитами, а не за найм. Удерживают на платформе то, что нельзя унести: поиск по рейтингу, приватные задания, алерты по сохранённым поискам, командные заметки, интеграция с ATS.

### Антиспам со стороны спроса

- Месячный лимит кредитов на контакт по плану; неиспользованные не переносятся.
- Запрос обязан ссылаться на вакансию (роль, вилка, локация или удалёнка) — шаблонные сообщения без вакансии отклоняются формой.
- Принятие < 15% за 30 дней при ≥ 20 запросах → лимит снижается вдвое, компании показывается предупреждение.
- Жалоба кандидата на спам → запрос помечается, 3 подтверждённые жалобы за 30 дней → приостановка поиска и ручная проверка.
- Массовые действия ограничены 25 кандидатами за раз и расходуют кредиты.

### Атрибуция найма

Найм не влияет на выручку, но нужен для метрик и истории успеха. Кандидат или компания отмечает найм; событие засчитывается, когда вторая сторона подтверждает. Кандидат получает значок «Нанят через greenbuild» (по желанию), компания — отметку в своём профиле.

### Против обратного отбора

Сильные инженеры часто не ищут работу активно. Для них — пассивный режим: профиль скрыт, но кандидат получает анонимные сигналы «3 компании искали ваш уровень Kubernetes на этой неделе» и может открыть профиль одной кнопкой. Попытки с флагом античита и непроверенные рейтинги не участвуют в выдаче по умолчанию.

Кандидат по умолчанию невидим для компаний; личность раскрывается только после явного принятия конкретного запроса и скрывается снова при отзыве.

### Правила

- **Режим по умолчанию — «Скрыт».** Игровой профиль при этом может быть публичным для других игроков; это отдельная настройка.
- **Поиск компаний доступен только с 18 лет** (подтверждение возраста при включении режима «Открыт»).
- **Анонимная карточка** содержит: навыки с рейтингами и доверительными интервалами, процентили, Verified, регион (страна или часовой пояс), уровень опыта, последнюю активность. Не содержит: имя, handle, аватар, ссылки на GitHub и соцсети, фото, точный город.
- **Запрос** обязан содержать роль, вилку, формат (офис, гибрид, удалёнка) и страны, где возможен найм. Один запрос — один кредит.
- **Принятие** раскрывает имя, handle, email для связи и ссылки, которые кандидат сам отметил. Компания видит только то, что кандидат разрешил.
- **Отклонение** не показывает компании причину напрямую; причины агрегируются в репутацию компании.
- **Отзыв согласия** возможен в любой момент: компания теряет доступ к личности кандидата в течение часа, её заметки о кандидате удаляются через 30 дней, в журнале аудита остаётся только факт контакта без персональных данных.
- **Блокировка компании** скрывает кандидата от неё полностью, включая анонимную выдачу.
- **Удаление аккаунта** автоматически отзывает все согласия и запускает удаление по политике хранения.
- Кандидат видит список компаний, которые открывали его анонимную карточку (после верификации компании) и отправляли запросы.

## Верификация компаний и доверие

Ни одна компания не видит кандидатов, пока не прошла верификацию; каждый рекрутер привязан к подтверждённому домену компании.

### Уровни верификации

| Уровень | Как подтверждается | Что открывает |
| --- | --- | --- |
| Домен | Письмо на адрес в домене компании + DNS TXT-запись | Приватные задания |
| Юрлицо | Регистрационный номер (EIN, номер в реестре ЕС), сверка с открытыми реестрами, платёжный метод на имя компании | Поиск и запросы на контакт |

### Защита от мошенничества

- Рекрутеры входят только с email домена компании; бесплатные почтовые домены запрещены.
- Ссылки в сообщениях проверяются по спискам фишинга; вложения запрещены.
- Кандидат видит у каждого запроса: верификацию, процент ответов компании, число жалоб.
- Жалоба «это не та компания» или «фишинг» → запрос скрывается, компания замораживается до ручной проверки.
- Скрининг компаний по санкционным спискам OFAC при верификации юрлица и раз в месяц.
- Кнопка «Сообщить о компании» в каждом запросе и в переписке.

| Scale | $1 499 / мес | 10 | 120 | 500 | Всё из Hire + ATS-интеграции, вебхуки, API, экспорт аудита, свои задания |
| Enterprise | договор | от 20 | по договору | по договору | SSO, DPA по шаблону клиента, выделенная поддержка |

Дополнительные кредиты — $15 за штуку; годовая оплата — скидка 20%; пробный период Hire — 14 дней с 5 кредитами.

### Почему подписка, а не процент от найма

- Агентская комиссия за найм обычно составляет 15–25% годовой зарплаты, но требует отслеживать найм — а общение уходит с платформы, и доход становится недоказуемым.
- Оплата за каждый контакт стимулирует массовые рассылки; подписка с лимитом кредитов стимулирует точный поиск.
- Подписка даёт предсказуемую выручку (MRR), удобную для инвесторов.
- План Assess продаётся без ликвидности маркетплейса: компания оценивает своих кандидатов, а платформа получает данные для валидации сигнала.

### Проверка цены

На этапе 1.5 каждому дизайн-партнёру предлагаем два варианта цены и фиксируем, какой принят; на этапе 3 — A/B-тест цены плана Hire на новых компаниях.

## Юнит-экономика

Бесплатный игрок стоит центы в месяц, поэтому десять компаний на плане Hire покрывают инфраструктуру этапа роста; все цифры — оценки для проверки на реальных данных.

| Показатель | Оценка | Основание |
| --- | --- | --- |
| Стоимость одной сессии песочницы | $0,001–0,003 | VM 8 vCPU / 32 GB ≈ $0,38/ч держит \~64 песочницы по 10 минут; с накладными расходами и пулом — до трёх раз больше |
| Инфраструктура на активного игрока в месяц | $0,05–0,15 | \~20 сессий в месяц + доля веба, базы и Redis |
| ARPA плана Hire | $499 / мес | Прайс-лист (гипотеза) |
| Прямые затраты на компанию в месяц | $20–40 | Эквайринг Stripe \~3%, верификация, поддержка |
| Валовая маржа на компанию | 90–95% | $499 минус прямые затраты и доля инфраструктуры |
| Точка покрытия инфраструктуры этапа роста ($1 500–5 000 / мес) | 4–11 компаний Hire | Инфраструктура / ARPA |
| Цель по окупаемости привлечения компании (CAC payback) | < 3 мес | Продажи основателем на этапах 1.5–3, без платной рекламы |
| Цель по оттоку компаний | < 4% в месяц | Для B2B-подписок малого и среднего бизнеса |

Главный риск экономики — не инфраструктура, а конверсия: если меньше 1 из 5 компаний на пробном периоде переходит на оплату, модель пересматривается до масштабирования.

## Политика хранения данных

Удаление выполняет worker по расписанию каждую ночь; каждое удаление пишется в журнал, а бэкапы с удалёнными данными истекают сами через 14 дней.

| Данные | Срок хранения | Что происходит потом |
| --- | --- | --- |
| Сырой лог сессии (Blob) | 90 дней | Удаляется; остаются сигналы античита |
| Запись Verified-сессии | 30 дней после решения | Удаляется; остаётся результат проверки |
| IP-адреса и данные устройства | 30 дней | Удаляются |
| Аккаунт после запроса на удаление | 30 дней | Персональные данные удаляются, попытки обезличиваются |
| Неактивный аккаунт | 3 года без входа | Письмо за 30 дней, затем удаление как по запросу |
| Личные поля у компании после отзыва согласия | 1 час | Доступ закрыт |
| Заметки компании о кандидате после отзыва | 30 дней | Удаляются |
| Переписка по запросу | Пока жив запрос + 1 год после последнего сообщения | Удаляется |
| Запросы на контакт без ответа | 14 дней до истечения, запись — 1 год | Обезличивается |

## Юридические требования

Ни одна компания не получает платный доступ к кандидатам, пока юрист по трудовому праву и защите данных США не подтвердил структуру продукта; это ворота этапа 3. Ниже — рабочий список рисков для обсуждения с юристом, а не юридическое заключение.

| Требование | Почему может касаться нас | Что делаем | Срок |
| --- | --- | --- | --- |
| FCRA (США) | Платформа, передающая работодателям оценки людей для решений о найме, может считаться агентством потребительской информации | Модель «кандидат сам делится результатом с конкретной компанией», без отчётов третьим лицам; заключение юриста | До этапа 3 |
| NYC Local Law 144 и аналогичные законы об ИИ в найме | Рейтинг и сортировка кандидатов для работодателя могут считаться автоматизированным инструментом решений о найме | Ежегодный независимый аудит на смещение, публикация итогов, уведомление кандидатов, методика в открытом доступе | До этапа 3 |
| Антидискриминация (Title VII, EEOC) | Косвенная дискриминация через рейтинг | Рейтинг не использует защищённые признаки; аудит смещения; запрет в условиях для компаний на дискриминационные фильтры | До этапа 3 |
| Санкции OFAC и экспортный контроль | Компании-плательщики в США, кандидаты из СНГ и Центральной Азии | Скрининг компаний; блок платных аккаунтов из комплексно санкционных юрисдикций; заключение юриста по обслуживанию кандидатов из регионов под ограничениями | До этапа 1.5 |
| GDPR и CCPA/CPRA | Пользователи из ЕС и Калифорнии | Раздел «Приватность», DPA, SCC, запросы субъектов | До этапа 2 |
| BIPA (Иллинойс) и законы о видеособеседованиях | Запись Verified-сессии с камерой | Отдельное письменное согласие, без биометрии, удаление через 30 дней | До Verified |
| Возраст (COPPA, GDPR) | Подростки могут прийти ради игры | Регистрация с 16 лет, поиск компаний — с 18 | До этапа 2 |
| Разрешение на работу при найме | Трансграничный найм | Платформа не является работодателем; компания указывает страны найма в вакансии и отвечает за оформление | До этапа 3 |
| Налоги с подписок | Продажи в разные штаты и страны | Stripe Tax | До этапа 1.5 |

### Юридическая структура

Для привлечения венчурных инвестиций стандарт — Delaware C-Corp, а не LLC; решение принимается до первого платящего клиента. Нужные документы: условия использования (отдельно для игроков и компаний), политика конфиденциальности, политика допустимого использования для компаний, шаблон DPA, политика cookie.

### Последовательность

1. Этапы 0–1.5: только дизайн-партнёры, 10 компаний, ручные продажи.
2. Этап 2: публичный запуск для кандидатов, компании — лист ожидания.
3. Этап 3: открытая регистрация компаний, пробный период, первые кейсы.

- [ ] Поиск, сохранённые поиски с алертами, шорт-листы, вакансии, заметки
